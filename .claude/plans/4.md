## Bounded context

No es un bounded context de negocio. Es infraestructura transversal de persistencia:

- `Platform.BuildingBlocks.Infrastructure`: `DbContext` base, convenciones EF, outbox técnico y registro Npgsql.
- `Platform.Identity.Infrastructure`: primer `DbContext` concreto, schema `identity` y migración inicial.
- `Identity.Domain` y `Identity.Application` no se tocan. No hay entidades de usuario, sesión, rol ni credenciales: eso es Etapa 2.
- No hay endpoints ni contratos públicos nuevos.
- Los demás módulos agregarán su `DbContext` cuando existan; no se crean proyectos ni schemas vacíos ahora.

## Criterios de aceptación

- `Platform.BuildingBlocks.Infrastructure` expone un `PlatformDbContext` base con las convenciones comunes y sin lógica de negocio.
- `Platform.Identity.Infrastructure` expone `IdentityDbContext` con schema `identity` y su historial de migraciones en `identity.__ef_migrations_history`.
- La migración inicial se aplica sobre una base limpia y crea `identity`, `identity.outbox_message` y el historial. No crea tablas de dominio de Identity.
- `identity.outbox_message` usa snake_case, PK `id uuid` generada en la aplicación (UUID v7), `seq bigint` identity para orden, `payload jsonb`, timestamps `timestamptz` y `status smallint`.
- NoTracking es el comportamiento global de consulta; `.AsTracking()` es explícito y está probado.
- Un `DateTime` con `Kind` distinto de `Utc` no se puede escribir en una columna `timestamptz`; uno UTC vuelve a leerse como UTC.
- Los enums persistidos usan `smallint`, con valores numéricos fijos. No se reutilizan ni renumeran valores.
- El proveedor Npgsql está pinneado y es compatible con EF Core 10.0.15. Licencia PostgreSQL (OSI, compatible con AGPL-3.0).
- Los tests de integración usan PostgreSQL real con Testcontainers, una base por corrida, nombre `platform_it_<utc>_<guid8>`, guard de borrado y usuario con `CREATEDB` y sin superusuario.
- `dotnet build backend/Platform.sln -c Release` y `dotnet format backend/Platform.sln --verify-no-changes` pasan.
- `dotnet ef migrations has-pending-model-changes` no reporta cambios después de generar la migración.
- Los tests de arquitectura siguen verdes y suman la dirección `Infrastructure` no depende de `Api` ni de otros módulos.
- No hay `Migrate()` automático al arrancar. En desarrollo la migración se aplica con comando explícito.
- No hay dependencias pagas ni secretos en el repositorio.

## Diseño de persistencia

### `DbContext` base o uno por módulo

Se usan las dos cosas, con límites claros:

- **Un `DbContext` concreto por módulo**, como pide ADR-0003. El primero es `IdentityDbContext`. Cada uno tiene su schema, su historial y sus configuraciones.
- **Un `PlatformDbContext` abstracto en `BuildingBlocks.Infrastructure`** solo para lo común: schema por defecto, NoTracking global, UTC, enums y nombres. No contiene entidades de negocio ni `DbSet` de módulos.
- La configuración de entidades de cada módulo va en su `DbContext`, no en BuildingBlocks.
- El outbox es técnico y opt-in: `IdentityDbContext` lo configura porque Identity publica eventos. No se obliga a todos los módulos a tener una tabla que todavía no usan.

Justificación: nueve módulos van a repetir las mismas convenciones. Tenerlas una vez evita que cada migración invente su propio mapeo de fechas, enums o nombres. El `DbContext` concreto mantiene el límite de módulo y permite migraciones independientes.

### Convenciones EF

| Tema | Decisión | Implementación | Motivo |
|---|---|---|---|
| Schema | Uno por módulo | `HasDefaultSchema(Schema)` en el base; `IdentityDbContext.SchemaName = "identity"` | ADR-0003. Límite visible en la base. |
| Historial | Uno por schema | `MigrationsHistoryTable("__ef_migrations_history", schema)` en `UsePlatformNpgsql` | Evita que dos contextos compartan historial. |
| Nombres | `snake_case` | `UseSnakeCaseNamingConvention()` con `EFCore.NamingConventions` 10.0.1 (Apache-2.0) | `docs/DATABASE.md` lo exige. Paquete maduro y compatible con Npgsql; menos código propio que una convención manual. |
| NoTracking | Global | `ChangeTracker.QueryTrackingBehavior = NoTracking` en el constructor del base; `.AsTracking()` explícito para lo que se guarda | Regla de `backend.md`. Evita mutaciones silenciosas. |
| Fechas | `timestamptz` UTC | Convención de modelo: todo `DateTime`/`DateTime?` se mapea a `timestamp with time zone`; Npgsql rechaza `Local` y `Unspecified` al escribir | UTC en base y backend. Falla rápido en vez de convertir en silencio. |
| Enums | `smallint` | Convención de modelo: `SetProviderClrType(typeof(short))` y `smallint`; valores explícitos | `docs/DATABASE.md`. Nunca renumerar. |
| IDs | `uuid` generado en la app | `ValueGeneratedNever()` en PKs; `Guid.CreateVersion7()` al crear | UUID v7 ordenable. Sin `gen_random_uuid()` ni generación en base. |
| Orden “reciente” | Columna secuencial | `seq bigint GENERATED BY DEFAULT AS IDENTITY` en outbox; índice por `seq` | Regla de `backend.md`: nunca ordenar por timestamp. |
| JSON | `jsonb` | `payload jsonb` en outbox | Consultable e indexable. |
| FKs | Dentro del schema | Se configuran cuando existan entidades. Entre schemas no hay FK | ADR-0003. |
| Concurrencia | `xmin` | Se agrega cuando el primer agregado editable lo necesite | No hay agregados en #4. |
| Soft delete | No | No hay necesidad funcional en #4 | `docs/DATABASE.md`. |

Nota: la tabla de historial de EF conserva las columnas `MigrationId` y `ProductVersion` por defecto. El nombre de tabla sí es `__ef_migrations_history`. Cambiar las columnas requiere reemplazar el historial de EF y no aporta valor.

### Tabla inicial de la migración de Identity

Se elige `identity.outbox_message`, no una entidad de Identity ni una migración vacía.

- **Outbox**: es técnico, está definido por ADR-0005, lo necesita Identity como productor y ejercita UUID, identity, `jsonb`, `timestamptz`, enum y snake_case. No adelanta dominio.
- **Entidad mínima de Identity**: adelanta `user`, `session` o `token` de Etapa 2 y obliga a decidir reglas de negocio antes de tiempo. Se descarta.
- **Migración vacía**: solo crea el schema y el historial. No demuestra tablas, columnas, índices ni convenciones. Se descarta.

No se crea `inbox_message` todavía: Identity no consume eventos en #4. Se agrega con el primer consumidor.

Estructura propuesta:

| Columna | Tipo | Regla |
|---|---|---|
| `id` | `uuid` | PK. Generado en la app con `Guid.CreateVersion7()`. `ValueGeneratedNever`. |
| `seq` | `bigint` | Identity, `GENERATED BY DEFAULT AS IDENTITY`. Orden de despacho. |
| `type` | `text` | Nombre del evento de integración. |
| `payload` | `jsonb` | Cuerpo serializado. |
| `occurred_at` | `timestamptz` | UTC, puesto por la app. |
| `processed_at` | `timestamptz` | Nullable. |
| `status` | `smallint` | Enum `OutboxMessageStatus`: `Pending = 0`, `Processed = 1`, `Failed = 2`. `CHECK (status BETWEEN 0 AND 2)`. |
| `attempts` | `smallint` | Default 0. |
| `last_error` | `text` | Nullable. |

Índice: `ix_outbox_message_processed_at_seq` sobre `(processed_at, seq)` con filtro parcial `processed_at IS NULL`. Sirve al despachador para tomar pendientes en orden sin escanear los procesados. No se agregan más índices sin consulta real.

### Registro y composición

`BuildingBlocks.Infrastructure` expone:

- `PlatformDbContext` abstracto.
- `UsePlatformNpgsql<TContext>(connectionString, schema)` para provider e historial.
- `AddPlatformDbContext<TContext>(services, connectionString, schema)`.
- `OutboxMessage`, `OutboxMessageStatus` y `ConfigureOutbox(modelBuilder)`.

`Identity.Infrastructure` expone:

- `IdentityDbContext` con `SchemaName = "identity"` y `DbSet<OutboxMessage>`.
- `AddIdentityPersistence(services, connectionString)`.
- `IdentityDbContextFactory` para `dotnet ef`.

`Program.cs`:

```csharp
var connectionString = builder.Configuration.GetConnectionString("Default")
    ?? throw new InvalidOperationException(
        "Falta ConnectionStrings:Default. Exportar ConnectionStrings__Default.");

builder.Services.AddIdentityPersistence(connectionString);
```

Clave: `ConnectionStrings:Default`; variable de entorno: `ConnectionStrings__Default`. Es la que ya documenta `.env.example` y el README del #3. No se guarda connection string en `appsettings*.json`.

El Host falla al arrancar si falta la connection string. Es fail-fast deliberado: un contexto registrado sin conexión no debe quedar latente. #5 agrega el health check de base; #4 solo demuestra que la composición arranca.

## Migraciones

### Qué crea la migración inicial

- Schema `identity`.
- Tabla `identity.outbox_message`.
- PK `pk_outbox_message` sobre `id`.
- Identity sobre `seq`.
- Índice parcial `ix_outbox_message_processed_at_seq`.
- Check `ck_outbox_message_status`.
- Historial `identity.__ef_migrations_history`.

No crea `user`, `user_session`, `refresh_token`, `user_role`, `email_verification_token`, `password_reset_token`, `audit_log` ni `inbox_message`. Eso llega con Etapa 2 o con el primer consumidor.

### Historial por contexto

Cada `DbContext` tiene su historial en su schema:

```text
identity.__ef_migrations_history
profiles.__ef_migrations_history   (cuando exista Profiles)
catalog.__ef_migrations_history    (cuando exista Catalog)
...
```

`UsePlatformNpgsql` fija `MigrationsHistoryTable("__ef_migrations_history", schema)` para que no se mezclen historiales. El atributo `[DbContext(typeof(IdentityDbContext))]` de la migración generada apunta al contexto correcto.

### Startup

No se llama `Database.Migrate()` ni `EnsureCreated()` al arrancar. Motivos:

- Migrar en startup con varias réplicas compite por el mismo historial.
- Un fallo de migración tumba el arranque sin contexto claro.
- `docs/DATABASE.md` exige comando explícito al deploy.

En desarrollo se usa el comando de arriba. En producción, Etapa 7 arma un bundle de migraciones y lo ejecuta como paso de deploy. No se implementa el bundle en #4.

### Script

No se agrega script propio todavía. Con un solo contexto, el comando de `dotnet ef` es suficiente y no hay lógica que envolver. Cuando existan varios contextos o el CI necesite aplicar migraciones, se agrega `infrastructure/scripts/db-migrate.sh` con la lista explícita de contextos. No se inventa ahora.

## Riesgos

| Riesgo | Impacto | Mitigación |
|---|---|---|
| Npgsql 10.0.4 exige EF Core `[10.0.15,11)` | Subir EF Core sin subir Npgsql rompe restore | Pins exactos en `Directory.Packages.props`; actualizar ambos juntos y correr build. |
| `EFCore.NamingConventions` puede atrasarse respecto de EF Core 11 | Bloquea upgrade futuro | Pin 10.0.1; si no hay versión para EF 11, evaluar convención propia o esperar. |
| NoTracking global | Un update sin `.AsTracking()` no guarda y no falla | Test explícito; revisión de repositorios; regla en `backend.md`. |
| `DateTime` con `Kind` local/unspecified | Npgsql lanza al guardar; un DTO mal parseado rompe el request | Falla rápida y visible. En Etapa 2 parsear con `DateTimeStyles.AdjustToUniversal` o usar `DateTimeOffset` en el borde. |
| Historial en schema equivocado | Dos contextos comparten historial o `dotnet ef` crea en `public` | `UsePlatformNpgsql` centraliza `MigrationsHistoryTable`; factory, DI y tests usan la misma extensión. |
| `identity` o `user` como identificadores | SQL inválido o quoting inesperado | Npgsql cita identificadores; `identity` no es palabra reservada. Test de migración sobre base limpia. |
| Testcontainers consume RAM y requiere Docker | Suite lenta o falla en CI sin Docker | Una suite de integración a la vez; CI #7 debe proveer Docker; documentar. |
| Imagen `postgis/postgis:17-3.7` solo amd64 | Lentitud en Apple Silicon | Mismo riesgo que #3; dueño en Linux amd64. Si aparece arm64, decidir emulación. |
| Contenedor de test usa superusuario | Incumple regla de usuario con `CREATEDB` y nada más | Fixture crea rol `platform_it` con `CREATEDB`, base propia y lo usa; el admin solo crea/borra. |
| Borrado de base de test | Se borra una base equivocada | Guard por regex `^platform_it_\d{8}T\d{6}Z_[0-9a-f]{8}$`; `DROP ... WITH (FORCE)` solo si coincide. |
| Outbox sin despachador | Tabla y entidad sin uso hasta #5/Etapa 2 | Es infraestructura definida por ADR-0005; el test prueba schema y convenciones. No se implementa dispatcher. |
| Host falla sin `ConnectionStrings__Default` | `dotnet run` no arranca sin exportar | Documentado en README y `.env.example`; fail-fast preferido a un contexto silenciosamente sin conexión. |
| Columnas del historial en PascalCase | Ruptura aparente de snake_case | Excepción conocida de EF; documentar. No justifica reemplazar el historial. |
| Migración inicial con `EnsureSchema` | Si el schema ya existe con otro dueño, falla | Base limpia en dev; en producción el deploy controla el schema. |
| `payload jsonb` sin validación | JSON inválido o evento incompatible | El productor serializa tipado; validación de contrato cuando exista el dispatcher. |
